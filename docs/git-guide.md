# Git 運用・開発ガイド

本プロジェクトにおける Git のブランチ運用、コミット規約、および開発フローに関するガイドラインです。
円滑な開発とコード品質の維持のため、原則として本手順に従って作業を行ってください。

---

## 1. ブランチ戦略

本プロジェクトでは、`main` ブランチを保護し、機能追加や修正は必ずトピックブランチを作成して作業します。

| ブランチ種別 | 命名規則 | 用途 |
| :--- | :--- | :--- |
| **メイン** | `main` | 安定版（本番/完成コード）。**直接コミット・直接 push は原則禁止** |
| **機能追加** | `feature/機能名` | 新機能の開発（例: `feature/user-auth`, `feature/sales-report`） |
| **バグ修正** | `fix/修正内容` | 不具合の修正（例: `fix/login-error`） |
| **設定・ドキュメント** | `chore/作業内容` | 環境設定、ドキュメント更新等（例: `chore/update-readme`） |

---

## 2. 日常の標準開発フロー

### Step 1: 最新の `main` からブランチを作成

作業を開始する前に、必ず最新の `main` ブランチから作業用ブランチを作成します。

```bash
# main ブランチに移動して最新化
git switch main
git pull origin main

# 作業用ブランチを作成して切り替え
git switch -c [ブランチ種別]/[機能等]
```

### Step 2: 実装・ローカル動作確認

コードの実装や設定ファイルの編集を行い、ローカル環境で正常に動作することを確認します。

### Step 3: 変更のコミット

コミットメッセージは、変更内容がひと目でわかるように**プレフィックス**を付与してください。

#### コミットメッセージのフォーマット

```text
<type>: <要約>

- <詳細1>
- <詳細2>
```

#### プレフィックス（`<type>`）の一覧

| type | 説明 |
| :--- | :--- |
| `feat:` | 新機能の追加 |
| `fix:` | バグ修正 |
| `refactor:` | リファクタリング（機能追加やバグ修正を行わないコード整理） |
| `docs:` | ドキュメントの修正・追加 |
| `chore:` | ビルドプロセスや補助ツールの変更、環境設定 |

#### コミット例

```bash
git add .
git commit -m "feat: ログイン機能の実装

- JWTトークン発行処理の追加
- ログインAPIのエンドポイント実装"
```

### Step 4: リモートリポジトリへ Push

作成したブランチを GitHub / GitLab 等のリモートリポジトリへ push します。

```bash
# 初回 push 時 (-u オプションでアップストリームを設定)
git push -u origin [ブランチ種別]/[機能等]
```

### Step 5: Pull Request (PR) の作成とマージ

1. GitHub 上で Pull Request を作成します。
2. 変更内容を確認（セルフレビューまたはチームレビュー）します。
3. 問題がなければ `main` ブランチへマージ（Merge）します。
4. マージ完了後、ローカルの不要になったブランチを削除します。

```bash
git switch main
git pull origin main
git branch -d feature/your-feature-name
```

## 3. Pull Request (PR) のレビュー・マージ手順

GitHub 上での PR 作成からマージ、マージ後の後片付けまでの手順です。

### Step 1: PR の作成

1. GitHub のリポジトリページを開き、「Compare & pull request」ボタンを押します。
2. **Title**: コミットメッセージと同様に `type: 概要` で記述します。
3. **Description**: 変更内容、確認したこと（ローカル動作確認済み等）を簡潔に書きます。

---

### Step 2: セルフレビュー（確認作業）

マージ前に「Files changed」タブを開き、以下をチェックします。

* 不要なデバッグログや一時ファイルが含まれていないか
* 意図しない設定変更が含まれていないか

---

### Step 3: マージ（Merge）の実行

GitHub の「Merge pull request」ボタンの横にある矢印から、マージ方法を選択します。

#### 💡 マージ方式の選び方

| マージ方式 | 概要 | おすすめ用途 |
| :--- | :--- | :--- |
| **Squash and merge** （★推奨） | ブランチ内の複数コミットを1つにまとめてマージ | 通常の機能追加・修正作業時（`main` の履歴が綺麗に保たれる） |
| **Create a merge commit** | 全コミット履歴をそのまま保持してマージ | 巨大な機能開発などで、各コミットの履歴を個別に残したい時 |
| **Rebase and merge** | コミットを `main` の直後に付け替えて直線化 | 履歴を一本化したい時（コンフリクト解決に注意が必要） |

> **基本方針:**  
> 機能追加（`feat/`）だけでなく、バグ修正（`fix/`）や環境設定（`chore/`）も含め、**原則として「Squash and merge」を選択**します。  
> 開発中の試行錯誤やタイポ修正などの細かなコミットを1つに凝縮して `main` に反映できるため、履歴が綺麗で追いやすくなります。

---

### Step 4: マージ後の後片付け（ローカル側の同期）

マージが完了したら、リモートブランチの削除ボタン（「Delete branch」）を押し、ローカル環境を最新化・整理します。

```bash
# 1. main ブランチに切り替えて最新化
git switch main
git pull origin main

# 2. マージ済みのローカルブランチを削除
git branch -d [作成したブランチ名]

# (任意) 古いリモートブランチ参照の掃除（※ローカル側のキャッシュ削除のみ。リモートのデータは消えません）
git fetch --prune

```

> **💡 `git fetch --prune` について**
> GitHub側ですでに削除されたリモートブランチの「ローカルに残っている参照メモ（古い看板）」を掃除するコマンドです。
> **リモートリポジトリ上のブランチやデータが消えることは絶対にない**ため、安心して定期的に実行して問題ありません。

## 4. トラブルシューティング（よくあるミスと対処法）

### Q1. `main` ブランチで直接作業してコミットしてしまった

まだ push していない場合は、新しいブランチを作成して `main` を1つ前の状態に戻すことで安全に救出できます。

```bash
# 1. 今の変更内容を含んだ新しいブランチを作成（切り替えはしない）
git branch feature/save-my-work

# 2. main ブランチを1つ前のコミット状態に戻す
git reset --hard HEAD~1

# 3. 新しいブランチに切り替えて作業を再開
git switch feature/save-my-work
```

### Q2. `main` ブランチで作業中だが、まだコミットしていない

そのまま新しいブランチを作成して切り替えれば、作業中の変更を持ったまま移動できます。

```bash
git switch -c feature/your-feature-name
```
